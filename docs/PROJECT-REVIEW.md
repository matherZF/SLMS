# 项目整体检查报告

## 1. 检查结论

项目已经从基础库存原型发展为围绕备品备件的数字化台账和全生命周期管理系统。现有主链路覆盖备件建档、入库上架、领用申请、流程审批、拣货确认、退库、盘点、报废、使用台账、设备运行数据刷新、权限和审计，具备科研项目演示与继续迭代的基础。

本次发现的主要问题是早期文档与当前代码差异较大：旧材料仍使用规划阶段的 `/api/v1`、`sp_*` 表名和早期状态定义，README 也未反映统一审批、动态角色权限、数据字典和使用台账等能力。新版文档已按当前实现重新整理，旧版仅保留作历史材料。

## 2. 已具备的主要能力

| 领域 | 当前能力 |
| --- | --- |
| 数字化台账 | 备件、分类、供应商、仓库、库位、批次、库存与流水 |

## 3. 当前风险与缺口

### 3.1 运行与数据安全

- 本地完整联调依赖 MySQL 服务可用；启动前需确认 MySQL 8.0+ 已运行且本地账号配置正确。
- Hibernate 自动更新表结构适合开发环境，正式生产建议改用版本化数据库迁移，避免不可控的结构变化。
- 设备系统视图需要固化字段类型、空值规则、更新频率和只读账号权限，并补充连接失败、回退和重复刷新策略。

### 3.2 流程引擎

- 当前适合简单串行审批。若以后需要会签、或签、并行网关、退回指定节点、转办和委托，需要扩展流程模型。
- 数量、金额和物品类型条件应逐步覆盖退库、报废、盘点差异等业务，并展示规则命中原因。
- 流程定义发布后应增加版本冻结：运行中单据继续使用发起时版本，新单据使用新版本。

### 3.3 业务追溯

- 金额判断依赖备件参考价格，建议增加价格来源、币种、生效日期和历史版本，避免修改主数据后影响历史口径。
- 使用台账可继续补充寿命预测版本、计算时间、输入快照和算法参数，使预测过程可复现。
- 关键附件、质检资料和报废依据可增加文件元数据、上传人、上传时间和业务关联关系。

### 3.4 权限与前端

- 后续权限设计应遵循“页面—按钮—接口”层级，避免早期权限编码被多个不同功能重复使用。
- 审批中心应保持统一名称，并确保列表、详情、流程轨迹、业务数据和操作区在桌面端及移动端一致。
- 无权限卡片隐藏后必须自动重排，不应在页面中留下大块空白。

### 3.5 测试与维护

- 自动化测试需继续覆盖审批条件边界、自动审批、重复提交、并发库存扣减、累计退库限制、越权访问和审计完整性。
- 建议增加 MySQL 集成测试，避免仅使用 H2 时遗漏枚举、索引、精度和 SQL 方言差异。
- 分页查询应避免集合抓取导致内存分页，并持续关注 Hibernate 的集合抓取分页警告。

## 4. 建议的后续优先级

1. 建立数据库迁移脚本并补充 MySQL 集成测试，优先保证数据结构和核心库存事务稳定。
2. 完成流程定义版本化、条件命中说明以及全部接入业务的审批回归测试。
3. 固化设备视图接口规范，完善定时刷新失败重试、人工刷新和预测结果追溯。
4. 补充价格版本、附件资料和寿命预测快照，增强全生命周期证据链。
5. 持续按前端规范统一审批中心和移动端页面，新增功能先设计权限及布局再开发。
