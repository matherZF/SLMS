# 备件需求预测

> 回答三个问题：**什么时候买**、**什么时候必须到货**、**这一单最少买多少**。
> 入口：`GET /api/spare-part-forecasts`（页面「需求预测」，与预警中心同权限 `page:alerts`）。

## 一、先说清楚能力边界

立项材料《备品备件数据分析与预测性维护研究》要求融合四类设备动态数据。对照源系统实际能给出的：

| 立项要求 | 源系统实况 | 本模块的处理 |
|---|---|---|
| 设备运行时长 | `SUM_HOURS` 列存在，**部分设备有值、部分恒为 0** | 用：有值的设备按 `HOURS` 口径算日耗；没值的设备自动退回件数/任务口径，不因缺一个字段整台作废 |
| 作业任务次数 | `SUM_QTY`（作业任务次数）有值 | 用：备件配 `TASKS` 口径即参与计算 |
| 故障报警代码 | 完全没有 | **做不了**。立项里「故障类型 ↔ 备件消耗」的关联规则无数据支撑 |
| 历史维修记录 | 无维修工单表 | 用 SP 自身的出库与台账更换记录替代 |
| 备件消耗 | 出库 + 使用台账 | ✅ 核心输入 |
| 库存 | `wms_inventory` | ✅ 核心输入 |

**结论：不做故障驱动，改做运行强度驱动磨损。**

设备干了多少活（时长 / 任务次数 / 处理件数）→ 备件磨掉多少 → 需要补多少。
这条链在机械上成立，只需要一张日汇总表（`dws_device_daily_stat` → `wms_device_stat_daily`），
而且可以用台账数据反向校验（实际寿命 vs 额定寿命，见第五节）。

如果后续能拿到故障码/维修工单，本模块的输入层可以加一路「故障频次 → 备件更换概率」，
但计算骨架（日耗 → 覆盖天数 → 到货日/下单日 → 补货量）不用改。

## 二、计算模型

### 单机日耗

每台设备上装的每个备件，日耗取下面五个口径的**最大值**：

```
运行时长口径：单机数量 × 设备日均运行小时 ÷ 额定运行小时    （备件配了 HOURS 口径）
任务次数口径：单机数量 × 设备日均任务次数 ÷ 额定任务次数    （备件配了 TASKS 口径）
件数口径：    单机数量 × 设备日均处理件数 ÷ 额定处理件数    （备件配了 QTY 口径）
周期口径：    单机数量 ÷ 更换周期                         （设备关联填了 change_cycle_days）
天数口径：    单机数量 ÷ 额定使用天数                      （备件配了 DAYS 口径）
```

取最大 = 谁先到期按谁补，与台账「建议更换日取早」是同一套逻辑。

**三个设备侧口径彼此独立。** 源表对部分设备不给运行时长，这时该设备就只用它有的口径；
一个字段缺失不会让整台设备退出计算——这是最容易写错的地方（写死成"必须有实时视图"
会让所有 HOURS 口径台账直接报错）。

### 备件级日耗

```
日均需求 D = Σ 各台设备的单机日耗
```

**只统计窗口内真有运行数据的设备。** 闲置设备不磨损，把它的装机数算进分母会把需求摊薄，
结果是补货补晚——这是这类算法最容易犯的错。

### 三个日期与一个数量

```
可用库存 S   = Σ(实存 − 已占用)
覆盖天数     = S ÷ D                                向下取整
预计缺货日   = 今天 + 覆盖天数
最迟到货日   = 预计缺货日 − 安全天数                 货必须在这天之前到
最晚采购日   = 最迟到货日 − 采购周期                 下单截点
最少补货量 Q = ⌈ D × (采购周期 + 安全天数) + 安全库存 − S ⌉
```

为什么到货日要提前「安全天数」：货掐着见底那天到等于没到——卸货、入库、上架、领用都要时间。
`安全天数` 默认 7 天（`spare-part.forecast.safety-days`），补货量的目标水位也用同一个数，
两个数保持一致，避免"补了货却仍显示要补"。

### 有采购周期 vs 没有采购周期

| 情况 | 输出的建议 | 页面标注 |
|---|---|---|
| 填了采购周期 | 「需在 X 前完成采购，Y 前到货，最少 N 件」 | 可预测 |
| 没填采购周期 | 「需在 Y 前到货 N 件；未填采购周期，交期按 7 天估算」 | 无采购周期 |
| 已过最迟到货日 | 「最迟到货日已过 N 天，需立即到货 N 件」 | 高级别 |
| 库存已见底 | 「库存已见底，需立即到货 N 件」 | 高级别 |

**没填采购周期照样预警**，只是算不出「下单日」而已。这里有过一个真 bug：库存只够 7 天
却因为没有采购周期算出"建议补 0"，被读成「暂不用补」。现在缺交期时按
`spare-part.forecast.default-lead-days`（默认 7 天）估算，并且**明确标注是估算值**——
交期估错意味着货到晚了，不能让这个数看起来像真的。

### 严重度

| 级别 | 条件 | 含义 |
|---|---|---|
| HIGH | 预计缺货日 ≤ 今天，或最晚采购日 ≤ 今天 | 现在就得动，再晚就断 |
| MEDIUM | 覆盖天数 ≤ 采购周期 + 安全天数 | 不紧急，但快到了 |
| 不告警 | 其他 | 只出现在预测页，不进预警中心 |

**缺采购周期不降级。** 没有交期数据不代表风险更低，恰恰相反：交期未知时更该早点动。

## 三、必须填的参数（不然算不出数）

按缺失后的表现排序：

| 缺什么 | 后果 | 页面表现 |
|---|---|---|
| 备件没关联任何设备 | 没有需求来源 | 状态「未关联设备」 |
| 既没寿命额定值也没更换周期 | 日耗为 0 | 状态「参数不足」 |
| 配了运行类口径、关联设备都不报对应字段 | 无法换算 | 状态「设备未上报」，写明缺哪个字段 |
| 没填采购周期 | 算不出下单日，但到货日与数量照给 | 状态「无采购周期」 |
| 设备有数据、备件没配对应口径 | 数据白拿 | 该设备依据里注明「有 XX 数据但未配对应口径，未参与计算」 |

页面上每条无法预测的备件都会列出「还缺这些」，是能直接照着补的清单。

> **当前测试数据的典型状态**：4 个备件里 4 个都配了 `DAYS` 口径，SP-004 另有 `QTY` 口径，
> 但设备关联里填的更换周期（10 天、30 天）与天数口径寿命往往接近，导致算出来的日耗
> 与产量基本无关。想让预测真正反映设备负荷，**应给备件补 `HOURS` 或 `QTY` 口径**
> （运行多少小时 / 处理多少件报废），这样设备多干就多耗，才是"基于设备状态"的预测。
> 页面每一行的依据里会直接提示哪个数据没被用上。

## 四、与其它预警的分工

`/api/alerts` 现在有四类：

| alertType | 判据 | 回答的问题 |
|---|---|---|
| `STOCK` | 可用库存 ≤ max(最低库存, 安全库存) 或设备级补货点 | 已经不够了 |
| `EXPIRY` | 批次 30 天内到期 | 快放坏了 |
| `LIFECYCLE` | 台账已用 ≥ 预警比例 | 装在设备上的快磨完了 |
| `FORECAST` | 见第二节严重度 | 按消耗速度，什么时候买、什么时候到、买多少 |

设备级补货点按设备算，但参数各归其位（V20 起）：

```
补货点(设备) = 备件档案.安全库存 + ⌈备件档案.采购周期 ÷ 本设备.更换周期⌉ × 本设备.单机数量
```

安全库存与采购周期只存在备件档案（`wms_product`）。放到设备关联上会让同一备件按设备重复计数，
也出现过同一 SKU 在备件档案填 0、在设备关联填 120、补货点一时是 0 一时是 130 的情况。

去重规则：**已经出了 `STOCK` 的备件不再出 `FORECAST`**——那种情况该补多少已经写在库存告警里了，
两条一起出现只会让人重复下单。

## 五、可校验性：实际寿命 vs 额定寿命

台账快照表 `wms_spare_part_usage_snapshot` 每次刷新记录一次设备累计量，
两次快照相减就能得到「这段时间设备干了多少活、消耗了多少备件」：

```
实际寿命 = Δ设备运行量 ÷ Δ消耗件数
```

与备件档案里的额定值比对：

- 实际明显短于额定 → 额定值偏乐观，或现场工况比设计恶劣，预测应按实际值修正
- 实际明显长于额定 → 额定值保守，或备件是预防性更换（没坏就换）

这也是判断"运行强度驱动"这条路走不走得通的直接证据。目前快照跨度不足（默认要
`spare-part.usage-sync.forecast-min-days` = 3 天以上），等夜间同步跑一段时间后可用。

## 六、配置项

```yaml
spare-part:
  forecast:
    production-window-days: 7   # 用最近几天的设备运行数据算日均
    safety-days: 7              # 到货后再多留几天用量（也用作到货日缓冲）
    default-lead-days: 7        # 没填采购周期时按几天估
```

对应环境变量：`SPARE_FORECAST_PRODUCTION_DAYS`、`SPARE_FORECAST_SAFETY_DAYS`、
`SPARE_FORECAST_DEFAULT_LEAD_DAYS`。

## 七、已知局限

1. **没有置信区间。** 用的是点估计（日均），没做需求分布拟合，因此也不给服务水平（如 95%）
   对应的安全库存。数据攒够 30 天以上、且日产量波动有明显统计特征时再引入。
2. **不管在途。** 采购单没有到货日期字段，建议补货量不扣减在途量。若同一备件已下单未到货，
   会重复建议。
3. **不管批次。** 备件有保质期时，补多了会临期。`EXPIRY` 告警与此独立，两者需要人一起看。
4. **产线调整有滞后。** 7 天窗口意味着设备停产一周后需求才会归零。
5. **运行时长依赖源系统上报。** 部分设备 `SUM_HOURS` 恒为 0 时，这些设备的 `HOURS` 口径不参与，
   只能用件数或任务次数口径；若三者都没有，该设备对该备件无贡献（页面会标「设备未上报」）。
