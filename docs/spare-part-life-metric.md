# 备件寿命多口径计量（取严）

## 一、要解决的问题

设备不是连续运行的：AGV 一天可能只跑 6 小时，其余时间在待机排队；输送线一小时处理几百件，也可能半天停线。这种情况下：

- **只按自然天数算**：一年 365 天听着合理，但设备实际只干了 2190 小时。厂家按"运行 8000 小时换轴承"定的定额，用天数去套会提前好几年就报到期，误换率高。
- **只按任务数算**：搬 1 件和搬 30 件都记 1 次任务，设备强度完全不同。
- **只按运行小时算**：SEND→FINISHED 里含排队等电梯、路径阻塞的时间，会把"空等"算成"在干活"。

结论：不同备件失效机理不同，不该二选一。做法是**每类备件配主口径 + 若干辅助口径，各算各的百分比，取最大值判定状态**——和汽车"里程到了或时间到了，谁先到谁保养"是同一套逻辑。

```
已用% = max( 运行小时/额定小时, 任务次数/额定次数, 处理件数/额定件数, 自然天数/额定天数 )
```

百分比最高的那条口径叫**主导口径**，寿命状态（使用中 / 寿命临近 / 已到寿命）按它判定，页面也优先展示它。

## 二、数据模型

迁移脚本：`backend/src/main/resources/db/migration/V11__life_metric_rules.sql`

| 位置 | 字段 | 说明 |
|---|---|---|
| `wms_product` | `life_metric_rules` TEXT | 规则 JSON：`[{"metric":"HOURS","rated":8000},{"metric":"TASKS","rated":200000}]`，第一条即主口径 |
| `wms_spare_part_usage` | `life_metric_rules` TEXT | 领用出库时从主数据**快照**下来，之后主数据改额定值不追溯影响已发出的备件 |
| `wms_spare_part_usage` | `baseline_piece_qty` / `current_piece_qty` | QTY 口径的基准值与当前累计值 |
| `wms_spare_part_usage_snapshot` | `life_metric` / `piece_qty` | 每次采集记下"当时是哪个口径主导"，事后可追溯 |

`life_metric` / `rated_life_value` 两列保留，语义收敛为"主口径"（= 规则第一条）。列表、导出、告警等既有读取路径不用改；存量数据在迁移里自动回填成一条规则，行为不变。

## 三、各口径的取数来源

| 口径 | 已用量算法 | 数据来源 |
|---|---|---|
| `HOURS` | `当前累计运行小时 − 基准` | 优先 `vw_sp_equipment_runtime.total_running_hours`；没有则回落 `wms_device_stat_daily` 按 `device_code` 累加 `running_hours` |
| `TASKS` | `当前累计任务数 − 基准` | 优先实时视图 `total_task_count`；没有则回落 `wms_device_stat_daily` 累加 `task_count` |
| `QTY` | `当前累计件数 − 基准` | 优先 `vw_sp_equipment_runtime.total_piece_qty`（可选列）；没有则回落 `wms_device_stat_daily` 按 `device_code` 累加 `total_qty` |
| `DAYS` | `今天 − 开始使用日` | 台账 `started_at`，不需要设备数据 |

**三个运行类口径都能退到每日汇总表**。WMS 侧只对部分设备上报 `SUM_HOURS`，
所以每个口径各自判断"这台设备有没有真报过"：

- 该列在窗口内全为 0 或 NULL → 视为「未上报」，返回无数据，而不是当成 0 累计
- 配了某个口径但关联设备都报不出对应数据 → 台账 `dataError` 写明缺哪个字段，不会静默用 0 算
- 三个口径可以混配，某个口径没数据不影响另一个

**关于兜底**：件数来自 ext-stat 定时同步落地的每日汇总表，累加的是"从同步起始日到今天"的量。因为台账只用到**差值**（当前 − 基准），同步开始得晚并不影响已用量准确性——这也是所有口径共同的基准机制。表里查不到该设备任何记录时返回"无数据"而不是 0（0 会被当成真实累计值建立基准，之后要很久才动，属于静默错误）。

## 四、怎么配置

备件主数据 → 编辑 → 管理属性 → 寿命计量：

- 第一行是**主口径**，可以选"不计算"
- 点"+ 增加辅助口径"追加，同一口径不能重复
- 每行各填自己的额定值，单位随口径自动切换（小时 / 次 / 件 / 天）
- 「寿命预警提前」填**提前多少天**（不再是百分比）：预计更换日临近这么多天就开始提醒
- 填 0 表示跟随系统配置（系统管理 → 系统配置 → 寿命预警提前天数，默认 3 天）；
  只有个别备件需要不同提前量时才填具体天数

典型配法：

| 备件 | 主口径 | 辅助口径 | 依据 |
|---|---|---|---|
| 行走减速机 | 运行小时 8000 | 任务次数 200000 | 疲劳磨损 + 启停冲击 |
| 输送线滚轮 | 处理件数 50000 | 运行小时 6000 | 按吞吐量磨损为主 |
| 皮带 | 处理件数 | 自然天数 730 | 橡胶老化 + 磨损 |
| 密封圈 | 自然天数 1095 | — | 按老化，跟运行无关 |
| 光电开关 | 任务次数 | 自然天数 | 动作次数为主，兼看老化 |

## 五、接口变化

`GET /api/spare-part-usages/{id}`、列表接口的返回体新增：

```json
{
  "lifeMetric": "QTY",
  "ratedLifeValue": 50000,
  "usedLifeValue": 41230,
  "usedPercent": 82,
  "lifeMetrics": [
    {"metric": "HOURS", "ratedLifeValue": 6000, "usedLifeValue": 3100, "remainingLifeValue": 2900, "usedPercent": 52, "primary": false},
    {"metric": "QTY",   "ratedLifeValue": 50000, "usedLifeValue": 41230, "remainingLifeValue": 8770, "usedPercent": 82, "primary": true}
  ],
  "baselinePieceQty": 120000,
  "currentPieceQty": 161230
}
```

顶层 4 个字段语义是"主导口径"，老前端不用改就是最该看的数字；`lifeMetrics` 是完整明细。

备件主数据的 `POST/PUT /api/products` 既接受新字段 `lifeMetricRules: [{metric, rated}]`，也继续接受老的单口径字段（自动折算成一条规则）。

## 六、常见问题

**Q：QTY 口径报"设备累计处理件数为空"？**
确认两件事：① `ext-stat.enabled=true` 且 WCS/WMS 同步任务已成功跑过；② 源库视图里 `device_code` 与备件台账的 `equipment_code` 完全一致（大小写、前后空格都算）。可执行：
```sql
SELECT device_code, COUNT(*), SUM(total_qty) FROM wms_device_stat_daily GROUP BY device_code;
```

**Q：同一台设备在 WCS 和 WMS 都有数据，会不会加错？**
默认跨源累加。如果两边有同号设备，在配置里指定只认一个源：
```yaml
spare-part:
  usage-sync:
    piece-source: WCS
```

**Q：想临时只看某一个口径？**
把其他口径的行删掉即可；台账已发出的不受影响（规则在领用时快照，改主数据只影响新发生的领用）。

## 七、使用设备从哪来

**设备挂在出库单的明细上，由领用人在每一行里选。** 备件大多是通用件——同一个轴承可能装在十几台输送机上，
基础数据里一条备件对多条设备关联是常态，系统无法知道这一批到底换到了哪台，所以必须由领用人指定。

> 必须是明细级而不是单据级：一张领用单可以有多个备件、装在不同设备上。
> 设备原先只存在单头，多明细跨设备时所有明细都被记到同一台，寿命、更换周期、需求预测全部失真。
> V26 起改挂明细（`wms_outbound_item.equipment_*`），单头只在「所有明细都指向同一台」时镜像一份供展示。

| 情况 | 下拉表现 |
|---|---|
| 所选备件只关联 1 台设备 | 自动选中，可改可清空 |
| 所选备件关联多台设备 | 列出这几台的并集，**留空不猜**，由领用人指定 |
| 所选备件未关联任何设备 | 下拉为空，提示「未关联设备」；台账记为未绑定，纯 DAYS 口径照常算 |

下拉候选取自「基础数据 → 设备档案 → 关联设备备件（`wms_equipment_part`）」，
接口是 `GET /api/equipments/by-product?productId=`。

台账落库的优先级：

| 顺序 | 来源 | 台账结果 |
|---|---|---|
| 1 | **这条明细**上选的关联设备 | 直接采用，`planned_cycle_days` 按「这一台 × 这一备件」那条关联取 |
| 2 | 明细未选、但单头有（老单据） | 采用单头那份 |
| 3 | 都未选、且该备件在基础数据唯一关联 1 台 | 逐条明细自动绑定各自那台 |
| 4 | 都未选、且未关联或多台关联 | 「未绑定设备」；若规则含 HOURS/TASKS/QTY 口径则状态为「待补基准」，明细里写明原因 |

纯 `DAYS` 口径不依赖设备，即使没关联也能正常算，状态不会挂起。

每行明细的候选 = 这一行那个备件在基础数据里绑定的设备，接口 `GET /api/equipments/by-product?productId=`；
单头（`wms_outbound_order.equipment_*`）不再作为录入项，只在所有明细同设备时镜像一份，
跨设备时留空，详情页据此显示「多台设备」。

关联可以晚于出库：出库那一刻还没关联的台账是「未绑定设备」，之后在基础数据里补上关联，
**刷新一次就会把设备号认回来**（纯 `DAYS` 口径也认，因为它不依赖设备库、不会被跳过）。
反过来，已经绑定了设备的台账不会被后续改动覆盖——出库当时装在哪台是既成事实，改设备要改的是基础数据里的关联，
而不是让历史台账跟着漂移。

```sql
-- 查看还有哪些台账没绑上设备（先确认是不是基础数据缺关联）
SELECT usage_no, sku, product_id, status, data_error
FROM wms_spare_part_usage WHERE equipment_id IS NULL AND status NOT IN ('CLOSED','RETURNED');
```

## 八、预计下次更换日

已用百分比只回答「磨损到什么程度」，不回答「什么时候该换」。后者由 `wms_spare_part_usage` 的六个新增字段承载（迁移脚本 V18）：

| 字段 | 含义 |
|---|---|
| `daily_rate` | 按历史快照拟合的日均消耗，单位随口径（件/天、小时/天、次/天） |
| `rate_sample_days` | 拟合所用样本的时间跨度（天）。不足 3 天只记录跨度、不给速率 |
| `expected_end_at` | 寿命耗尽日：所有口径里**最早**到期的那一天 |
| `planned_cycle_days` | 出库时从设备-备件关联快照的更换周期 |
| `planned_end_at` | 计划更换日 = 开始使用时间 + 更换周期 |
| `expected_replace_at` | **建议更换日**，上面两个日期取早 |

### 速率怎么算

取该台账的快照序列（`wms_spare_part_usage_snapshot`）里首尾两个有效累计值做差，除以实际时间跨度：

```
日均消耗 = (最新累计 − 最早累计) ÷ 跨度天数
寿命耗尽日 = 今天 + ⌈剩余寿命 ÷ 日均消耗⌉
```

以下情况一律不预测，页面显示「已累积 N 天」而不是一个随手瞎编的日期：

- 跨度不足 `spare-part.usage-sync.forecast-min-days`（默认 3 天）
- 设备闲置，速率为 0
- 累计值回退（设备换过或重置过计数器）

### 为什么取「最早」而不是「最严」

「主导口径」按已用百分比选，回答谁磨损得快；「更换日」要按谁先耗尽选。两者常常不是同一条——
例如某备件配置了「自然使用 30 天」+「处理 10 万件」，装上才 25 天时：

- 主导口径是 DAYS（83%），QTY 才 1%
- 但按当前速率 QTY 还要 990 天才耗尽，DAYS 只剩 5 天
- 建议更换日必须是 5 天后，不能是 990 天后

代码里用 `LifeMetrics.soonest()` 与 `LifeMetrics.dominant()` 分别取，两者不可混用。

### 寿命（备件档案）与更换周期（设备关联）的区别

| | 位置 | 语义 | 单位 |
|---|---|---|---|
| 额定寿命 | 备件基础数据 | 技术上能撑多久 | 小时/次/件/天，可多口径 |
| 更换周期 | 设备-备件关联 | 这台设备上计划多久换一次 | 天 |

两者不必相等：技术上能撑 120 天、规定 90 天预防性更换，是完全正常的业务场景。
建议更换日取两者计算结果的较早者——实际消耗比计划快就提前，反之按保养计划执行。

`planned_cycle_days` 在出库时快照进台账，之后改设备档案不追溯已发出的备件。

V18 之前建的历史台账由 V19（`V19__backfill_usage_forecast.sql`）补一次：DAYS 口径的到期日，
以及能从当前设备关联查到的更换周期都会填上。HOURS/TASKS/QTY 口径必须靠多天快照拟合速率，
迁移里既不补齐也不编造，等下一次人工刷新或夜间自动同步；在此之前页面显示「已累积 N 天」。
关联关系本身在「基础数据 → 设备台账 → 关联备件」里维护，一个备件装多台设备就建多条关联；要让某台设备参与寿命统计，必须在这里挂上。

### 设备关联上只有两项，采购周期与安全库存属于备件档案

`wms_equipment_part` 只存「这台设备上的这个备件」独有的数据：

| 字段 | 为什么在设备侧 |
|---|---|
| 单机数量 `installed_qty` | 同一备件在不同设备上装几个可以不同 |
| 更换周期 `change_cycle_days` | 同型号设备在不同产线负荷不同，换件节奏不同 |

采购周期与安全库存曾在关联表上也各存一份，V20 已收回到备件档案：

- **采购周期**：由供应商决定，一个 SKU 只有一条供应渠道，填在设备上必然重复且可能互相矛盾。
- **安全库存**：仓库对该 SKU 的保底量，库存本来就是多台设备共享的。设备级填 10 件装 3 台设备，
  到底该备 10 件还是 30 件没有答案，还会让同一备件的补货点按设备各算一遍。

设备级补货点仍按设备计算，但参数来源分开：

```
补货点(设备) = 备件档案.安全库存 + ⌈备件档案.采购周期 ÷ 本设备.更换周期⌉ × 本设备.单机数量
```

V20 迁移时把已录入的设备级数值按「取最大值」提升到备件档案（现场 SP-001 的 120、SP-004 的 100 由此而来），
再删除关联表的两列。若这些值原本是按单台设备估的，需要到备件档案按仓库整体重新确认。
