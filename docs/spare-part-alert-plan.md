# 备件预警与需求预测方案

> 目标：库存不断货、更换不误期，每条提醒都能直接指导动作——**什么时候买、什么时候到、买多少**。
> 本文是业务口径方案，不含代码实现；文末第八节列出待确认事项，确认后才动系统。

---

## 一、范围

| 类别 | 维度 | 回答的问题 |
|---|---|---|
| 库存预警 | 备件 | 已经不够了，现在就得买 |
| 备件更换预警 | 设备 × 备件 | 装在某台设备上的那一件该换了 |
| 库存预测 | 备件 | 按消耗速度，什么时候会不够、什么时候下单 |

触发方式：每天 09:00 自动计算一次。

## 二、数据基础

### 2.1 备件主数据（`wms_product`）

| 字段 | 用途 | 现状 |
|---|---|---|
| 采购周期 `procurement_lead_days` | 下单到到货的天数，决定「最晚采购日」 | 已有 |
| 安全库存 `safety_stock` | 仓库对该 SKU 的保底量 | 已有 |
| 使用寿命 `life_metric` + 额定值 | 按时间：DAYS（天）、HOURS（运行小时）；按量：TASKS（任务次数）、QTY（件数） | 已有四种口径 |
| 最低库存 `min_stock` | 与「安全库存」语义重叠 | **建议弃用或改名**，见下 |

**关于「最低库存」与「安全库存」**：两个阈值并存时现场不知道该看哪个，预警判据也会出现「按哪个算」的歧义。建议只保留安全库存作为预警阈值；若最低库存另有用途（如陈列下限），建议改名为「常备量」并在预警说明里注明不参与计算。

### 2.1.1 安全库存怎么定（维护指南）

**先分清两个量**，混在一起会设错：

| | 定义 | 作用 |
|---|---|---|
| 安全库存 | 只应对意外（需求超预期、到货延迟、来料不良） | 日常消耗不该动用它 |
| 补货点 | **采购周期内常规需求 + 安全库存** | 库存降到它就下单 |

用户常说的「最少该备多少才不停机」指的是补货点，不是安全库存。

**计算公式**

```
采购周期内常规需求 = 装机总数 ÷ 更换周期 × 采购周期
安全库存           = 常规需求 × 系数（见下表）
补货点             = 常规需求 + 安全库存
```

**分档取值**

| 类型 | 特征 | 安全库存 |
|---|---|---|
| 易损易耗、通用、单价低 | 消耗快且有规律 | 常规需求的 50%~100% |
| 一般易损件 | 中等频率 | 常规需求的 30%~50% |
| 耐耗件（一年以上） | 几年不动 | **1 套 = 单台装机数**，不按需求算 |
| 长交期 / 进口 / 定制件 | 买不到就长期停机 | 1 套整机用量 + 常规需求，关键件可备 2 套 |
| 高价 + 交期短 | 占资金但随时能买 | 0 或 1，需要时现买（可做寄售 / VMI） |

**耐耗件必须换思路**：公式会算出小数（3 年一换、采购 45 天 → 需求 0.8 个），但真换的时候一次就得拿「单台装机数」个。耐耗件吃的是「能不能及时买到」，不是「用得多快」。

**算例**：备件 A，10 台设备 × 2 个 = 装机 20，更换周期 30 天，采购周期 15 天

```
常规需求 = 20 ÷ 30 × 15 = 10 个
安全库存 = 10 × 50%    =  5 个
补货点   = 15 个
```

不按「10 台同时坏」设 20 个——同时损毁是低概率事件且可加急，为它压 20 个的资金不划算；只有停机代价极高（整线停）时才提到一次更换的最大量。

**资金占用按二维分档**

| | 停机影响大 | 停机影响小 |
|---|---|---|
| 单价高 | 重点保：足量 + 找短交期供应商 | 0~1 件现买，或寄售 / VMI |
| 单价低 | 多备，压不了多少钱 | 1 个最小单元即可 |

**维护节奏**：初始按公式算 → 每季度回顾（重点看是否出现过「等料停机」、是否有「一年没动过」的件）→ 换供应商、增删设备、调整更换周期时立即重算。

### 2.2 设备关联（`wms_equipment_part`）

| 字段 | 用途 |
|---|---|
| 装机数量 `installed_qty` | 这台设备上装了几个 |
| 更换周期 `change_cycle_days` | 这台设备计划多久换一次（保养节奏） |

采购周期与安全库存**不在**这里维护：前者由供应商决定，一个 SKU 只有一条供应渠道；后者是仓库共享保底量，按设备填写会重复计数（一个轴承装 3 台设备各填 10 件，仓库该备 10 件还是 30 件没有答案）。此项 V20 迁移已落地。

### 2.3 外部数据

| 数据 | 来源 | 落地时间 |
|---|---|---|
| 设备日运行数据（工时 / 任务数 / 件数） | WCS/WMS 汇总表或视图 | 每天 01:30 同步 |
| 使用台账快照 | 上述数据 + 台账刷新 | 每天 02:00 同步 |
| 库存 | 本系统 | 实时 |

**约束**：`SUM_HOURS` 只有部分设备能取到；部分产线设备不在 WMS 设备清单内，拿不到产量。因此「按量算寿命」只对部分备件成立，其余必须有兜底（见 3.2）。

## 三、核心口径

### 3.1 单机日耗 D（件/天）

同一备件可能同时存在多种口径，取**最保守**（数值最大）的那个：

```
单机日耗 = max(
    装机数 × 日均运行小时   ÷ 额定小时,      // HOURS
    装机数 × 日均任务数     ÷ 额定次数,      // TASKS
    装机数 × 日均件数       ÷ 额定件数,      // QTY
    装机数 ÷ 更换周期,                       // 保养节奏
    装机数 ÷ 寿命天数                        // DAYS
)
备件日耗 D = Σ 各在产设备的单机日耗
```

### 3.2 三层兜底（数据不全时）

| 优先级 | 来源 | 适用 |
|---|---|---|
| 1 | 设备运行数据（工时 / 任务数 / 件数） | 设备上报了对应字段 |
| 2 | 出库流水日均 | 有历史出库且非成批领用 |
| 3 | 装机数 ÷ 更换周期 | 什么数据都没有 |

**不建议把历史出库流水作为主口径**：系统上线初期流水几乎为空，算出来恒为 0 会导致永远不报警；且备件常成批领用（一次领 10 件用一个月），按周平均会失真。出库流水适合做校验——两种口径都有时取大。

### 3.3 三个时间节点

```
剩余可支撑天数  D_cover = 当前库存 ÷ D
见底日           = 今天 + D_cover
最迟到货日       = 见底日 − 安全天数            （默认 7 天）
最晚采购日       = 最迟到货日 − 采购周期
最少补货量   Q   = ⌈D × (采购周期 + 安全天数) + 安全库存 − 当前库存⌉
```

未填采购周期时，按 `default-lead-days`（默认 7 天）估算，并在提醒里注明「交期按 7 天估算，以供应商实际交期为准」。

## 四、三类预警设计

### 4.1 库存预警（已发生）

| 项 | 内容 |
|---|---|
| 判据 | 可用库存 ≤ **补货点**（触发）；库存 ≤ **安全库存**（升级） |
| 维度 | 备件 |
| 严重度 | 见下方双阈值分级 |
| 提醒 | `{备件} 已低于安全库存（当前 {库存} / 安全库存 {阈值}），建议补 {Q} 件，请及时采购。` |

**双阈值分级：触发看补货点，定级看安全库存**

补货点 ≥ 安全库存（采购周期内需求为 0 时两者相等），二者回答不同问题，不是二选一：

| 库存区间 | 状态 | 动作 | 严重度 |
|---|---|---|---|
| 库存 > 补货点 | 正常 | 不动 | — |
| 安全库存 < 库存 ≤ 补货点 | 该下单了，常规交期来得及 | 按采购周期正常采购 | MEDIUM |
| 0 < 库存 ≤ 安全库存 | 已在动用缓冲 | 加急 / 催货 / 调拨 | HIGH |
| 库存 = 0 | 已停机待料 | 紧急处理 | HIGH |

系统现状：设备级已按此实现（`reorderPoint` 触发 + `stock <= safetyStock` 定级），但补货点只算单台（见 4b）；备件级缺补货点，直接拿安全库存当阈值（见 4c）。

**采购需求量 Q 的取数口径**

不要用补货点算——补货点已含需求，再算一遍会重复。目标是「货到之后库存至少还能撑到下一次补货」：

```
Q = ⌈日耗 × (采购周期 + 安全天数) + 安全库存 − 当前库存⌉
```

算例（日耗 0.67、采购周期 15、安全天数 7、安全库存 5、当前库存 12、补货点 15）：

| 算法 | Q | 到货后库存 | 评价 |
|---|---|---|---|
| 补到安全库存 | 不买 | 2 | 错，会停机 |
| 补到补货点 | 3 | 5 | 勉强，刚到安全库存就得再买 |
| **按公式** | **8** | **10** | 能撑到下一轮 |

**三个尚未纳入的修正项**

1. **在途量**：已下单未到货的应扣除，否则重复采购。系统当前**没有采购管理模块**（只有出库、入库、盘点，无采购单），在途量不可得；一期靠告警落表后的「已处理」状态手工标记规避。
2. **最小起订量 / 包装倍数**：供应商按盒、按卷供货时 Q 需向上取整到包装倍数，需要则备件主数据加字段。
3. **最大库存上限**：Q 需按库容或资金上限封顶。

**说明**：原方案文案为「XXX 已低于安全库存，请及时采购」。建议补上当前库存、阈值和建议采购量——只有「低了」这个结论，仓库还要自己去查该买多少。

### 4.2 备件更换预警（将要发生）

| 项 | 内容 |
|---|---|
| 判据 | 预计更换日 − 今天 ≤ 提前量 |
| 预计更换日 | 取两者较早：①寿命按实际消耗速度耗尽的那天 ②装上时间 + 更换周期 |
| 提前量 | **3 天（可配置）**，固定值，不与采购周期联动 |
| 维度 | 设备 × 备件（使用台账） |
| 严重度 | 已到期或已超期为 HIGH；**预计更换时库存不够**为 HIGH；其余 MEDIUM |
| 提醒 | `{设备} 的 {备件} 预计 {日期} 到期（已用 {百分比}），请及时更换。` |
| 提醒（库存不足时） | `{设备} 的 {备件} 预计 {日期} 到期，但当前库存 {N} 不足以支撑本次更换（需 {M}），请加急采购。` |

**关键：这条提醒只负责「安排检修」，不负责「提前买货」。**

提前量不要取 `max(3 天, 采购周期)`。换件需要的货，由**库存预测**负责提前买——库存预测在计算未来需出库量时，会把预计更换日落在窗口内的更换按装机数量一次性计入（见 4.3）。这样：

- 库存充足时：只有更换日前的 3 天提醒，内容就是「该安排人去换了」，不会提前 30 天喊采购。
- 库存不够时：库存预测早在「更换日 − 采购周期 − 安全天数」就报了要买多少；更换提醒只在 3 天前出现，作为检修安排。
- 极端情况（到 3 天前才发现没货）：更换提醒升级为 HIGH 并附带加急采购文案，属于兜底，不是主路径。

**不要用百分比做判据。**原实现是「已用 ≥ 80%」，对一年寿命的件意味着提前 73 天，对 10 天寿命的件只提前 2 天，很不稳定。
已改为按剩余天数判断（`SparePartUsageService.updateStatus`），长短寿命的件口径一致；
备件档案上的百分比字段（`life_warning_percent`）随之停用，列保留只为兼容历史台账快照。

**提前量在哪配**：只有一个值——系统管理 → 系统配置 →「寿命预警提前天数」
（`spare-part.life.warning-days`，默认 3 天）。备件档案上的「寿命预警提前(天)」填 0 表示跟随它，
非 0 才是该备件单独设的（长寿命件想早点提醒就调大）。

**台账状态（`NEAR_DUE` / `DUE`）与更换预警用的是同一个值**，改一处两边同时生效；
两者若拆成两个参数，会出现台账列表显示「在用」但预警已经报出来的矛盾。

> 早期版本里曾并存「寿命预警提前天数」与「更换预警提前量」两个配置项，实际是同一件事，
> 而且只有后者被代码读取（前者改了系统无反应）。已合并为 `spare-part.life.warning-days`。

### 4.3 库存预测（将要发生）

| 项 | 内容 |
|---|---|
| 判据 | `D_cover ≤ 采购周期 + 安全天数`（未填采购周期时按 7 天兜底） |
| 维度 | 备件 |
| 去重 | 已触发库存预警的备件不再重复出预测 |
| 提醒一 | `{备件} 预计 {日期} 将低于安全库存，建议补 {Q} 件，请及时采购。` |
| 提醒二 | `{备件} 预计 {日期} 消耗完毕，请在 {最晚采购日} 前采购、{最迟到货日} 前到货，最少采购 {Q} 件。` |
| 提醒三（无采购周期） | `{备件} 预计 {日期} 消耗完毕，请在 {最迟到货日} 前到货，最少采购 {Q} 件（未填采购周期，交期按 7 天估算，以实际为准）。` |

**为什么不用固定的「提前 7 天」**：预警的意义是留出下单到货的时间。采购周期 30 天的件，若等库存只剩 7 天才提醒，下单当天就已注定断货 23 天。

```
库存还能撑的天数 D_cover
├─ D > 37        安全，不提醒
├─ 30 < D ≤ 37   该下单了，还来得及（MEDIUM）
├─ 0 < D ≤ 30    常规交期已来不及，需加急（HIGH）
└─ D = 0         已断货
        （以采购周期 30 天 + 安全天数 7 天为例）
```

**「需出库量」要包含两类消耗**：① 按日耗推算的持续消耗；② 未来窗口内到期要换的那批（台账预计更换日落在窗口内的，按装机数量一次性计入）。只算①会漏掉马上要来的批量换件。

**这一条是整套方案的枢纽**：正因为需出库量里含了集中换件，库存预测才会在「更换日 − 采购周期 − 安全天数」那个时点就发现不够、提前报警。更换预警因此不必承担提前采购的职责，只需提前 3 天喊人去换。若不做这一步，换件引起的库存缺口就只能等更换预警触发时才暴露，那时采购一定来不及。

## 六、每天 09:00 的执行链路

```
01:30  拉设备日运行数据            （已有定时任务）
02:00  刷新使用台账快照            （已有定时任务）
09:00  计算三类预警 → 落表 → 推送  （新增）
```

**前提**：WMS 源库跑批必须早于 01:30，否则拉到的是前天数据。此项需与 WMS 侧确认。

定时任务要点：

- 沿用现有的 `SchedulerLockService` 加锁，避免多实例重复计算
- 落表字段建议：`日期、类型、维度、备件、设备、台账、严重度、当前库存、阈值、日耗、可支撑天数、见底日、最迟到货日、最晚采购日、建议采购量、提醒内容、处理状态`
- 页面改为读表，`/api/alerts` 实时接口保留，用于「立即重算」
- 去重：同一（类型, 备件, 设备, 台账）24 小时内只提醒一次；已处理/已忽略的不再出现
- **服务重启当天自动补跑一次**（`AlertSnapshotScheduler.catchUpOnBoot`）。现场重启是常态（发版、改配置项），
  只靠 09:00 一次的话，重启后到第二天 09:00 之前站内提醒一直是空的。
  判据是「今天是否已跑过批」：预警表里没有今天的 `updated_at` 就补跑一次，已经跑过就不重复算。

### 6.1 计数口径必须全站统一

工作台首页、预警中心、菜单/底部 Tab 角标，**都必须读落表**，任一处用实时算都会出现自相矛盾：

| 读法 | 后果 |
|---|---|
| 首页实时算、预警页读表 | 09:00 之前首页提示「有 N 条预警」，点进去列表是空的 |
| 角标实时算、列表读表 | 角标红了但列表没东西，或反之 |

实现：`DashboardService.summary()` 返回 `alertCount`（`OPEN` 条数）与 `alertUnread`（`OPEN 且未读`），
角标接口 `GET /api/alerts/unread-count` 与它们同源。实时接口只在「立即重算」按钮里用。

### 6.2 APP 端（移动/WebView）的提醒入口

移动端的常驻提示有三处，缺一处就等于没有站内提醒：

1. 底部 Tab「预警」上的未读红点
2. 顶栏铃铛入口（带角标，点进去就是预警中心）
3. APP 原生端的手机通知栏（新增未读预警时弹出，见 7.1）

前两处与系统通知共用同一次轮询：APP 原生端每 3 分钟拉一次 `GET /api/alerts?status=OPEN`（顺便算未读角标），
Web / 手机浏览器每 5 分钟拉一次 `unread-count`；两者都在路由变化时立即刷新——
在预警页点了「已处理 / 全部标已读」之后回到首页，角标要立刻消失，通知栏里对应的通知也一起收掉。
移动端列表点卡片即标记已读（按操作按钮不算，用 `.stop` 隔开）。

#### 6.2.1 消息弹框的已读规则

铃铛弹框（`AlertNoticeSheet.vue`）按「常见 APP 消息中心」的口径做，三条规则：

1. **角标只数未读**：`GET /api/notifications/count` = 未读预警（`read_flag=0`）+ 未读待审批，已读不计数；
2. **已读不消失**：点开某条只是红点消失、计数 -1，消息继续留在列表里，只是变淡（标题常规字重、图标降透明度）；
3. **每条各自有红点**：未读条目的分类图标右上角挂红点，已读没有；点过的条目即使业务上已经处理完
   （例如审批通过后源任务消失），仍能靠已读回执的快照继续挂在列表里。

实现：`GET/POST /api/notifications`（列表 / 已读 / 全部已读）+ 表 `wms_notification_read`
（唯一键 `username + category + target_id`，存已读时间与内容快照，回执保留 30 天）。
预警的已读仍落在 `wms_alert_user_state.read_flag`，不重复存回执。
列表排序：未读在前、同时段按时间倒序，最多 60 条。

### 7.1 已实现：APP 端系统通知（本地通知）

APP 是 Capacitor 壳，服务端在客户内网，接不了 FCM / 厂商推送通道，所以走「前端轮询 + 本地通知」：

- 插件：`@capacitor/local-notifications`，通知渠道 `wms_alert_v1`（重要性 HIGH，横幅 + 声音），
  状态栏图标 `ic_stat_alert`（铃铛剪影），颜色 `#1E54D8`。
- 入口：`frontend/src/composables/useMessagePush.js`，由 `AppLayout.vue` 在进入有 `page:alerts` 权限的布局时启动。
- 去重：`dedupKey + severity` 存 `localStorage`，同一条预警只响一次，级别从中升高会再响一次；
  首次进入（或换账号后重新登录）只记基线，不把历史未读一次性推出去，避免装包即刷屏。
- 合并：一次新增超过 3 条时只详推前 3 条，其余合并成一条「另有 N 条新预警」。
- 交互：点通知直达预警页；在预警页标已读 / 已处理会同时清掉通知栏里对应的通知。
- 权限：Android 13+ 首次进入请求一次 `POST_NOTIFICATIONS`，被拒后不再反复弹窗，页面角标照常工作。

边界：轮询跑在 WebView 里，APP 切到后台会被系统挂起，所以提醒时机是「APP 在前台」或「切回前台立刻补一次」；
APP 被系统清掉后不会推送。要做到熄屏也实时推送，必须上 FCM / 厂商通道（需外网）或企业微信机器人（二期方案）。
